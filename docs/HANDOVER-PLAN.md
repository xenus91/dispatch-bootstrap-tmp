| Проверено | Результат |

не проверив ни одной строки.

**Что было сломано на самом деле:**

| Проблема | Следствие |
|---|---|
| `tsc --noEmit` на solution-tsconfig | Проверялось 0 файлов — 28 реальных ошибок прошли незамеченными |
| `tsconfig.node.json` не включал `src/api` | **Весь API-слой не проверялся типами вообще** |

## 1. Главное за минуту

Проект технически крепкий: MAX-бот, панель диспетчера, oRPC/Drizzle, подпись initData HMAC-SHA256, блокировка перебора, журнал доступа. Но он **ни разу не разворачивался у заказчика**: в репозитории нет ни Docker, ни обратного прокси, ни миграций, ни CI, ни даже рабочего `.env.example`.

**Юридический блокер один — и он ровно в той части, которую вы назвали:**

> База сейчас — **Turso/libSQL, то есть хостинг за пределами РФ**. С 1 июля 2025 г. ч. 5 ст. 18 152-ФЗ — прямой запрет записывать ПДн граждан РФ в базы за пределами страны (штраф по ч. 8 ст. 13.11 КоАП до 6 млн ₽, повторно до 18 млн ₽). Переезд на PostgreSQL на российском VPS — это не «хочу Postgres», это требование закона. Хорошо, что работа ложится в одну корзину.

**Второй юридический риск — в коде.** В билд зашита сторонняя аналитика Runable (`r.lilstts.com`), в `index.html` подключены Google Fonts. Оба — трансграничная передача данных пользователей без уведомления в Роскомнадзора (ст. 12 152-ФЗ). Убирается за час работы.

**Третье — функциональный пробел.** Ваш пункт «возможность обновления вебхуков» в панели закрыт на 80%: подписка, отписка, список подписок и диагностика интеграции **уже реализованы** (`pages/settings.tsx`, `routes/settings.ts`). Не хватает эксплуатационной части: проверки достижимости, ротации секрета, журнала доставки и — главное — **сторожа вебхука** на сервере. В референсном проекте для Telegram это уже решено (`scripts/tg-webhook-guard.sh`), для MAX сделаем аналог.

**Четвёртое — пробел по 152-ФЗ в коде.** Нет выгрузки и удаления ПДн (права субъекта по ст. 14–17), нет согласия на обработку (ст. 9), нет политики `/privacy` (ст. 18.1), нет аудит-лога административных действий.

### 3.1 Ответ про сертификат — подробно

В референсном проекте домен панели — **`.ru`**, и он работает с сертификатом **Let's Encrypt**, который Caddy выпускает сам через ACME HTTP-01. Значит, «.ru требует российского УЦ» — неверное допущение: Let's Encrypt выдаёт сертификаты для `.ru` (в политике ISRG `.ru` в списке допустимых зон, а OFAC-ослабление прямо оставляет сертификаты доступными для негосударственных организаций РФ).

**Как это работает у нас:**

1. A-запись домена → IP VPS заказчика.
2. Caddy сам идёт в Let's Encrypt по ACME HTTP-01 и выпускает сертификат. Нужен открытый порт 80 и корректный DNS. Всё.
3. Перевыпуск — автоматически, Caddy сам.
4. MAX принимает такой сертификат: доверенный УЦ, домен в SAN, цепочка полная, порт 443. Ровно то, что требует `POST /subscriptions`.

**Обязательные проверки перед сдачей:**

| Проверка | Зачем | Команда |
|---|---|---|
| Предполёт на санкционные и региональные ограничения | С июня 2026 LE-SA v1.7 добавил санкционную оговорку: для подсанкционных лиц сертификаты не выдаются, а держатель обязан сам запросить отзыв. Для IP под блокировкой РКН — технические сбои выпуска | `certbot certonly --dry-run -d <домен>.ru` — не тратит лимит |
| Доступность LE из сети заказчика | Если сеть режет — сертификат не выпустится | `curl -I https://letsencrypt.org` → 200 |
| Лимит выпусков | 50 сертификатов в неделю на домен | Не перевыпускать в цикле |

**План Б (если LE не выпустит):** российский УЦ → Caddy с монтированием сертификата:
```
<домен> {
    tls /certs/<домен>.crt /certs/<домен>.key
    reverse_proxy app:4200
}
```
Сертификаты от Госуслуг признаются только в России — для MAX и для зарубежных браузеров не подойдут, нужен коммерческий УЦ.

> **Разделить два разных сертификата, чтобы не запутаться:**
> - **Сертификат панели** — Let's Encrypt, для браузеров и для приёма вебхуков MAX.
> - **Корни Минцифры** (`certs/russian-trusted-root-ca.pem`, `russian-trusted-sub-ca.pem`) — для исходящих запросов приложения к `platform-api2.max.ru`. В нашем проекте они уже вшиты в код (`api/max/tls.ts`), поэтому переменные окружения не нужны; в образ кладём их для `curl` и диагностики.

## 4. Целевая архитектура

```
                    Интернет
                       │  80/tcp (ACME) + 443/tcp
                       ▼
        ┌──────────────────────────────┐
        │  caddy:2-alpine              │  ← Let's Encrypt сам, автоперевыпуск
        │  reverse_proxy → app:4200    │  ← security headers, rate limit
        │  volumes: caddy_data/config  │
        └──────────────┬───────────────┘
                       │ внутренняя сеть docker
        ┌──────────────▼───────────────┐      ┌────────────────────────┐
        │  app                         │      │  db                    │
        │  oven/bun:1.3.14-alpine      │─────▶│  postgres:16-alpine    │
        │  non-root uid 10001          │      │  только во внутренней  │
        │  read_only fs, cap_drop ALL  │      │  сети, порт наружу нет │
        │  /api → Hono+oRPC             │      │  volume: pgdata        │
        │  /  → статика dist/          │      │  pg_dump → /backups    │
        │  планировщик в процессе      │      └────────────────────────┘
        └────────────────────────────┘
```

**Отличия от референса и почему:**

| Решение | Обоснование |
|---|---|
| Bun, а не Node | Родной рантайм проекта; `Bun.serve` раздаёт статику и API одним процессом |
| `expose` вместо `ports` для app и db | Наружу торчит только 80/443 контейнера Caddy. Прямого доступа к БД из интернета нет в принципе |
| Postgres 16 отдельным сервисом | Независимые бэкапы (`pg_dump` без остановки приложения) и независимый рестарт |
| Планировщик остаётся в процессе | `setInterval` 60 с работает штатно на VPS; самопинг (`SCHEDULER_SELF_PING`) нужен только для платформ с засыпанием → выключаем |
| Один инстанс приложения | `instances: 1` в PM2 — верно: планировщик и long-polling не должны работать в двух процессах |

### Поток B. PostgreSQL (чистая база)

**B1. Схема: `packages/web/src/api/database/schema.ts` → pg-диалект.**

| Было (sqlite-core) | Стало (pg-core) |
|---|---|
| `sqliteTable` | `pgTable` |
| `integer("id").primaryKey({autoIncrement:true})` | `serial("id").primaryKey()` |
| `integer("x", {mode:"timestamp"})` | `timestamp("x", {withTimezone:true, mode:"date"})` |
| `integer("x", {mode:"boolean"})` | `boolean("x")` |
| `real("x")` | `doublePrecision("x")` |
| `text(...)` для JSON-полей | оставить `text` (совместимость), либо `jsonb` — на усмотрение |

`$defaultFn(now)`, `.notNull().default(...)` и `.returning()` в Drizzle для Postgres работают как есть — код менять не нужно.

**B2. Клиент БД.** `packages/web/src/api/database/__client.ts` — файл **защищён платформой** (хеш в `.runable/protected-files.json`). Для клиентской версии это ограничение снимается, но правильный ход — не трогать защищённые файлы, а добавить рядом:

- новый `packages/web/src/api/database/client.ts` — `drizzle-orm/node-postgres` + пул `pg`: `max: 10`, `idleTimeoutMillis: 30_000`, `connectionTimeoutMillis: 5_000`
- `packages/web/src/api/database/index.ts` (не защищён) переключается с `export { db } from "./__client"` на экспорт из нового клиента

**B3. `packages/web/drizzle.config.ts`:** `dialect: "turso"` → `"postgresql"`, `dbCredentials` → `{ url: process.env.DATABASE_URL }`.

**B4. Перейти с `db:push` на настоящие миграции.** Сейчас схема накатывается `drizzle-kit push` — разовый слепок, не версионируется и не откатывается. Для коммерческой поставки: `drizzle-kit generate` → SQL-файлы в `packages/web/drizzle/` → `drizzle-kit migrate` при старте контейнера. В `db:push` в проде не идти.

**B5. Проверка совместимости запросов.** Главный риск — «тихие» расхождения в SQL-семантике. Проверить точечно:
- `inArray` / `notInArray` с пустым массивом (в SQLite это `WHERE 1=0`, в PG надо убедиться, что Drizzle не генерирует `IN ()`)
- **Регистр в `LIKE`**: SQLite `LIKE` регистронезависимый для ASCII, PG — регистрозависимый. Поиск по телефону идёт через `normalizePhone` — проверить, что сравнение по нормализованному значению, а не по `LIKE`
- Деление: в PG `/` на целых даёт целое — если где-то есть целочисленное деление, нужна правка
- Сортировка дат: в SQLite `integer` timestamp (секунды), в PG — `timestamptz`. **На чистой базе конверсия данных не нужна**, но все `mode:"timestamp"`-поля надо перевести на `timestamp` и убедиться, что приложение пишет и читает их одинаково
- `onConflictDoUpdate` — в PG требует явного `target`, в коде он есть
- `LIMIT`/`OFFSET` и `ORDER BY` с NULL — поведение при сортировке по nullable-полям различается

**B6. Сид начальных данных.** Чистая база → нужен скрипт сида: первый админ (уже есть `ensureSeedAdmin()`), базовые справочники (типы контейнеров, типы операций), настройки по умолчанию. Вынести в `scripts/seed.ts` с идемпотентностью.

**B7. Прогон всех сценариев на PG.** Создание заявки → назначение водителю → отметки на остановках → тревоги → напоминания. Отдельно проверить, что планировщик корректно отрабатывает паттерн «захват строки» (`UPDATE ... WHERE ... IS NULL` для `reminder_sent_at` / `late_alert_at`) — на PG он должен отработать ровно один раз.

**Трудоёмкость: 1.5 дня** (было бы 3 с миграцией данных — чистая база съела 1.5 дня).

### Поток D. Caddy, TLS, безопасность периметра

**D1. `Caddyfile`** — по референсу, с доменом заказчика:

```
<домен> {
    reverse_proxy app:4200
}

www.<домен> {
    redir https://<домен>{uri} permanent
}
```

**D2. Заголовки безопасности — с одной оговоркой.** Панель работает как iframe/mini-app внутри MAX, поэтому:

```
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Content-Security-Policy: frame-ancestors 'self' https://*.max.ru https://max.ru
```

`X-Frame-Options: DENY` здесь **сломает мини-приложение** — использовать только `frame-ancestors` в CSP.

**D3. Rate limit** на `/api/cron/tick` и `/api/rpc/auth/*` — на уровне Caddy.

**D4. Проверка достижимости вебхука.** MAX требует: HTTPS на 443, `HTTP 200` в течение 30 секунд, имя домена в CN/SAN, полная цепочка, самоподписанные не принимаются. Панель уже отвечает `200` на `/api/webhooks/max` (обработчик отвечает сразу, не блокируясь на обработке — правильно).

## 8. Операционные грабли — сразу в документацию

Из опыта референсного проекта; в нашем случае надо учесть заранее:

| Грабля | Что делаем |
|---|---|
| `docker compose up -d --no-recreate` не подхватывает новый образ | Только `--force-recreate` (или `up -d --build`) |
| Скрипт деплоя перетирает `.env` целиком | Ручные переменные держать в отдельном файле, деплой не должен перезаписывать `.env` |
| Hairpin NAT: из контейнера не достучаться до своего же домена | Проверять через `curl --resolve <домен>:443:127.0.0.1` |
| Build cache раздувает диск (в референсе — 16.4 ГБ) | `docker builder prune -af` после серии сборок + `disk-guard` в cron + лимит кэша в `/etc/docker/daemon.json` |
| `journald` и логи Docker съедают диск | `logrotate.d/docker` (maxsize 50M), `journalctl --vacuum-size=200M` |
| Хост рвёт SSH на kex после нескольких подряд подключений | `MaxStartouts 30:30:100`, `LoginGraceTime 30` в `sshd_config` |
| Build на сервере идёт 4–5 мин, вывод теряется | `nohup ... > /tmp/build.log 2>&1` |
| Deploy-ключ на сервере read-only → `git push` не работает | Выдать право записи в настройках deploy key или пушить с машины разработчика |
| Heredoc в CI-скриптах → раннер вставляет префикс в каждую строку | Команды однострочные |
| Корни Минцифры: Sub CA действует до **06.03.2027** | Напоминание в RUNBOOK и в документации |
