# Эксплуатационные процедуры

Как система работает изнутри: планировщик, тревоги, очистка данных, вебхуки,
бэкапы. Для того, кто администрирует развёртывание.

---

## Планировщик

Планировщик живёт **внутри процесса приложения** и выполняет проход раз в
минуту (`api/lib/scheduler.ts`). Отдельной службы нет — это сделано намеренно:
при перезапуске контейнера ничего не теряется, а состояние «захвачено /
не захвачено» хранится в БД, а не в памяти.

**Один проход делает четыре вещи:**

| Что | Логика |
|---|---|
| Напоминание водителю | За `reminderMinutes` до планового прибытия и **не позже** самого плана. Отметка `reminder_sent_at` ставится до отправки, повторов нет |
| Тревога «опаздывает» | Через `stopLateMinutes` после плана, если водитель не отметил прибытие на текущей остановке |
| Повтор тревоги диспетчерам | Неподтверждённая тревога через `alertEscalateMinutes` уходит повторно. Отметка — в БД (`claimWindow` на 3 дня), не в памяти |
| Проверки доступа | Применение авто-приостановки, чистка старых сессий, чистка обработанных событий MAX |

### Проверить, что планировщик жив

```bash
docker compose exec -T db psql -U dispatch -d dispatch \
  -c "SELECT value FROM settings WHERE key='scheduler:heartbeat';"
```

В панели: «Настройки» → «Интеграция с MAX» → индикатор планировщика. Зелёный —
работает, красный — пауза (в скобках — сколько минут).

### Внешний триггер

На обычном VPS планировщику не нужен внешний триггер. Он нужен там, где
хостинг усыпляет приложение без входящих запросов: тогда процесс раз в минуту
будит себя сам через публичный адрес.

```bash
# включается переменной SCHEDULER_SELF_PING=1
# плюс нужны WEBSITE_URL (https) и CRON_SECRET
```

Ручной запуск прохода:

```bash
set -a; . ./.env; set +a
curl -s "https://<домен>/api/cron/tick?key=$CRON_SECRET&src=manual"
# {"ok":true,"ms":42}
```

## Тревоги

Типы тревог:

| Тип | Когда | Кто видит |
|---|---|---|
| `stop_late` | Нет отметки прибытия через N минут после плана | Диспетчеры |
| `late` | Общий признак опоздания | Диспетчеры |
| `failure` | Срыв заявки | Диспетчеры, администраторы |
| `no_contact` | Нет связи с водителем | Диспетчеры |
| `security` | События безопасности | Администраторы |

Тревога подтверждается вручную в карточке заявки. Неподтверждённая тревога
повторно уходит диспетчерам через `alertEscalateMinutes`.

Критичные тревоги приходят всем, даже тем, кто включил режим «только мои
заявки».

## Очистка данных

Чистится автоматически:

| Данные | Срок | Кто чистит |
|---|---|---|
| `processed_updates` (обработанные события MAX) | 3 дня | планировщик |
| `sessions` с истёкшим сроком | по TTL | планировщик |
| Сессии сотрудников с истёкшим доступом | автоматически | `runAccessChecks` |

Ручная очистка нужна для истории заявок. **Удаляйте строго по конкретным
идентификаторам, а не по телефону или по шаблону имени** — массовый UPDATE по
телефону обнуляет историю реального сотрудника, и восстановить её можно
только из дампа.

```bash
# посмотреть, что будет затронуто — сначала SELECT
docker compose exec -T db psql -U dispatch -d dispatch \
  -c "SELECT id, number, status, created_at FROM requests WHERE created_at < now() - interval '3 years' LIMIT 20;"

# и только потом удалять, по конкретным id
docker compose exec -T db psql -U dispatch -d dispatch \
  -c "DELETE FROM requests WHERE id IN (123, 456);"
```

## Вебхуки

### Как это работает

1. Бот MAX отправляет событие на `https://<домен>/api/webhooks/max`.
2. Приложение сверяет заголовок `X-Max-Bot-Api-Secret` с `MAX_WEBHOOK_SECRET`.
3. Отвечает `200` **сразу**, не дожидаясь обработки — MAX повторяет доставку при
   не-2xx, и ответ должен уложиться в 30 секунд.
4. Обработка идёт в фоне. Повторные доставки отсекаются таблицей
   `processed_updates` — действие водителя не выполнится дважды.

### Почему подписка слетает

MAX снимает подписку, если endpoint долго недоступен. При деплое контейнер
`app` пересоздаётся, Caddy несколько секунд отдаёт 502 — этого достаточно.

События при этом **не теряются**: MAX накапливает их и доставляет повторно после
восстановления. Но пока подписки нет, новые события не приходят вовсе.

### Сторож

```bash
cat > /etc/cron.d/max-webhook-guard <<'EOF'
*/5 * * * * /opt/dispatch-containers/scripts/max-webhook-guard.sh >> /var/log/max-webhook-guard.log 2>&1
EOF
```

Раз в 5 минут сверяет `GET /subscriptions` и переподписывается, если нашего
адреса в списке нет. Лог: `/var/log/max-webhook-guard.log`.

### Журнал доставки

Каждое входящее событие пишется в `webhook_events` с исходом: `processed`,
`duplicate`, `bad_secret`, `bad_json`, `failed`. Записи живут 14 дней, дальше
чистит планировщик.

Смотреть можно в панели: «Настройки» → «Доставка событий за сутки».

```sql
SELECT outcome, count(*) FROM webhook_events
WHERE created_at > now() - interval '24 hours' GROUP BY outcome;
```

| Соотношение | Что это значит |
|---|---|
| processed растёт | всё в порядке |
| duplicate много, processed ноль | события приходят, но не проходят проверку секрета — проверьте `MAX_WEBHOOK_SECRET` и ротацию |
| bad_secret растёт | MAX присылает события с другим секретом — нужна переподписка |
| total = 0 | события не доходят: проверьте подписку (`GET /subscriptions`) и сторож |

### Long polling

`MAX_LONG_POLLING=1` — только для разработки. MAX прямо предупреждает: при
активной подписке на вебхук события через polling не приходят. В продакшене
`MAX_LONG_POLLING=0`.

## Бэкапы

```bash
# ежедневно в 03:30
30 3 * * * /opt/dispatch-containers/scripts/backup.sh >> /var/log/dispatch-backup.log 2>&1
```

- Формат: `pg_dump --clean --if-exists`, сжатие gzip -9.
- Хранение: 7 дней, `/opt/dispatch-containers/backups`, права `600`.
- Восстановление: `scripts/backup.sh restore <файл>`.

**Дампы лежат на том же сервере.** Для настоящей защиты нужна копия на другом
хосте — настройте выгрузку по SFTP или rsync на отдельное хранилище.

Проверка восстановления — в
[`NEW-VPS-FROM-SCRATCH.md`](./NEW-VPS-FROM-SCRATCH.md), шаг 6.

## Гигиена диска

Docker build-cache способен занять десятки гигабайт. Регулярно:

```bash
docker builder prune -af --filter "until=24h"
docker image prune -af --filter "until=72h"
journalctl --vacuum-size=200M
docker system df
```

Лимит кэша в `/etc/docker/daemon.json`:

```json
{ "builder": { "gc": { "enabled": true, "defaultKeepStorage": "2GB", "reservedSpace": "1GB" } } }
```

Ротация логов Docker уже настроена в `docker-compose.yml`
(`max-size: 20m`, `max-file: 5`).

## Наблюдаемость

Что есть из коробки:

| Инструмент | Где смотреть |
|---|---|
| Health-check | `GET /api/health`, `docker compose ps` |
| Пульс планировщика | `settings` → `scheduler:heartbeat`, индикатор в панели |
| Логи приложения | `docker compose logs -f app` |
| Логи БД | `docker compose logs -f db` |
| Логи Caddy | `docker compose logs caddy` |
| Журнал доступа | Панель → «Сотрудники» → карточка → «Журнал доступа» |
| Тревоги | Панель → заявка |

Что стоит добавить на стороне клиента (не входит в поставку):

- внешний мониторинг доступности (ping по `/api/health` раз в минуту);
- уведомление в MAX или на почту, если приложение не отвечает;
- алерт на заполнение диска выше 70%.

## Обслуживание MAX

**Корни Минцифры** вшиты в код (`api/max/tls.ts`) и в образ (`certs/`).
Sub CA Минцифры действует **до 06.03.2027** — после этой даты корни нужно
обновить. Положить новые файлы в `certs/` и пересобрать образ.

**Смена токена бота:** кабинет `business.max.ru` → «Чат-боты» → «Настройки» →
новый токен → вписать в `.env` → `docker compose up -d --force-recreate app` →
переподписаться на вебхук.
